py_wasm_module

Build Python into a self-contained WebAssembly module: CPython and the sources of py_library targets, callable from any WebAssembly runtime, with no Python interpreter on the host.

The module is CPython built for wasm32-wasi and linked with an in-module implementation of the WASI functions it would otherwise import, so that it imports nothing and a runtime that provides no host functions at all can instantiate it. Inside it run the unmodified sources of the py_library targets named by deps, served by an importer over a bundle linked into the module, together with the standard library as bytecode. By default the interpreter is started and the entry module imported at build time, with Wizer, and the memory snapshot becomes the module, so a call does not pay for start-up.

Setup

Nothing beyond depending on rules_venv and registering, with rules_python, a hermetic Python toolchain of a version the rule supports: 3.13, 3.14, and 3.15 once rules_python maps it to a final release. Modules are built with a py_wasm_toolchain, and rules_venv registers one for each such version and each Linux and macOS host (x86_64 and arm64) and Windows host (x86_64), made of the wasm32-wasi build of that CPython release from periareon/cpython-wasi-build, the wasi-sdk release that built it and Wizer, which its py_wasm extension fetches when a module is first built. The CPython comes in variants, the default being the fastest under Bazel's runtime; see "The CPython" below. A compiler or CPython of one's own is another py_wasm_toolchain; see "Toolchains" below.

Requirements

  • A hermetic rules_python toolchain of the module's python_version, a final release. Its C headers compile the module's host code and its interpreter produces the bytecode for the one in the module, so the two must be the same X.Y and a pre-release, whose bytecode and ABI may differ, is refused; the rule fails on either, and the build tools check again when they run.
  • A py_wasm_toolchain for that version on the host, and Wizer when preinitialize is on. The rule fails when preinitialize has no Wizer.
  • Code that runs on CPython for WASI: a source the embedded interpreter cannot import fails at build time with its traceback when preinitialize is on, else at the first call.

Use

load("@rules_venv//python:defs.bzl", "py_library")
load("@rules_venv//python/wasm:defs.bzl", "py_wasm_module")

py_library(
    name = "entry",
    srcs = ["entry.py"],
    deps = ["//my_rules:lib"],
)

py_wasm_module(
    name = "my_rules",
    entry = "my_rules.wasm.entry",
    exports = ["run"],
    python_version = "3.14",
    deps = [":entry"],
)

The entry module defines one function per export, taking the input of the call as bytes and returning bytes, or (bytes, code) to set the call's return code:

import json

def run(payload: bytes) -> bytes:
    request = json.loads(payload)
    ...
    return json.dumps(response).encode("utf-8")

Calling the module

The module exports its memory as memory, an allocator, and one function per entry of exports:

allocate(size: u32, align: u32) -> u32            the address of `size` bytes
<export>(input: u32, input_len: u32,
         out_ptr: u32, out_len: u32) -> u32       the return code

A host writes the input into memory it obtained from allocate, calls the export with the addresses of two more words to receive the output's address and length, and reads the output back from memory. The return code is 0, or the code the function returned with (bytes, code), or 2 when it raised, in which case the output holds the traceback and what was written to standard error. With Python's wasmtime package:

import wasmtime

store = wasmtime.Store(wasmtime.Engine())
module = wasmtime.Module.from_file(store.engine, "my_rules.wasm")
exports = wasmtime.Instance(store, module, []).exports(store)
memory = exports["memory"]

payload = json.dumps(request).encode("utf-8")
input_ptr = exports["allocate"](store, len(payload), 1)
memory.write(store, payload, input_ptr)
out = exports["allocate"](store, 8, 4)
code = exports["run"](store, input_ptr, len(payload), out, out + 4)
out_ptr = int.from_bytes(memory.read(store, out, out + 4), "little")
out_len = int.from_bytes(memory.read(store, out + 4, out + 8), "little")
output = bytes(memory.read(store, out_ptr, out_ptr + out_len))

A call changes the instance's memory, and instances are independent, so a host that wants every call to be a function of its input alone instantiates the module per call. Any runtime that can instantiate a module without imports and call exports with integer arguments can be the host; examples/py_wasm_module in the rules_venv repository has a Bazel repository rule calling a module with repository_ctx.execute_wasm this way.

What a call can do

Nothing outside the module: no files, network, clock or processes. Standard output and error are captured inside the module; the error stream of a failed call is returned with the traceback. A program that needs the outside world receives what it needs in its input and describes what it wants done in its output, in rounds if need be. Bytes cross the boundary unchanged in both directions.

The CPython

The CPython in a module is a release built for wasm32-wasi by periareon/cpython-wasi-build, pinned by version and hash in python/wasm/private/versions.bzl together with the wasi-sdk release that built it. Of that build the rule uses pyconfig.h, libpython and the libraries of the modules compiled into it, and its standard library as source; the public headers are the rules_python toolchain's, and the bytecode is produced at build time by that toolchain's interpreter, which is why the two must be the same version.

Each version comes in variants that differ in how the interpreter is compiled, because the runtime decides which build is fast. Bazel runs a module with Chicory, which compiles each wasm function to one JVM method and interprets, silently, any function too large for one; CPython's evaluation loop is such a function in its normal build, and a Python-heavy call then spends most of its time in that interpreter (a solver call measured 88 s against 2.5 s). So:

  • stock: CPython's own WASI build, as brettcannon/cpython-wasi-build publishes it; the fastest under wasmtime.
  • small-eval: built for size with the evaluation loop kept under the limit, so that Chicory compiles everything; about ten times faster there.
  • trampoline (3.14 and newer): the tail-calling interpreter turned into a call-threaded one, with no function anywhere near the limit; the fastest under Chicory, about twice as slow as stock under wasmtime.

The default is the fastest under Chicory: trampoline for 3.14, small-eval for 3.13, stock where it is the only build. Modules run elsewhere pick another with the //python/wasm:cpython_variant flag, in .bazelrc or on the command line; it applies to every version at once, and a version without the variant asked for fails saying which it has:

build --@rules_venv//python/wasm:cpython_variant=stock

Toolchains

A module is built with a py_wasm_toolchain: the clang of a wasi-sdk, a CPython built for wasm32-wasi (libpython, the libraries of its modules, its pyconfig.h and its standard library), the flags that CPython links with, and Wizer. Two of rules_python's toolchains take part as well, resolved for the same Python version: its C toolchain, for the headers, and its exec tools toolchain, for the interpreter that produces the module's bytecode.

The defaults

rules_venv registers a toolchain for every Python version pinned in python/wasm/private/versions.bzl that the resolved rules_python maps to a final release, 3.13 and 3.14 today, for Linux and macOS on x86_64 and arm64 and for Windows on x86_64. Its py_wasm extension declares the archives and writes the toolchains into the repository @rules_venv_py_wasm_toolchains. Nothing is fetched until a module is built, and then only what the resolved toolchain needs. Each toolchain is gated on rules_python's is_python_X.Y, which a module's python_version sets, so the embedded CPython always matches the Python toolchain the module is built with; a version rules_python maps to a pre-release is left out, and the rule refuses one, since its bytecode and ABI may differ from the release's.

One of your own

Declare a py_wasm_toolchain and a toolchain gated on is_python_X.Y, as in the documentation of py_wasm_toolchain, and register it with register_toolchains in MODULE.bazel or with --extra_toolchains. A root module's toolchains take precedence over rules_venv's, which remain as the fallback for other versions and hosts. Reasons to: a CPython built differently, with other configure options or patches; a version or host rules_venv has no build for; a policy of building from source; or a newer wasi-sdk, which must be the release that built the CPython so that their wasi-libc agree. linkopts and stdlib of the toolchain cover smaller adjustments: what the CPython links against, and which standard library modules go into a module.

Replacing one archive

To keep a default toolchain but swap one of its parts, point the extension's repository for it elsewhere. In MODULE.bazel:

py_wasm = use_extension("@rules_venv//python/wasm:extensions.bzl", "py_wasm")
override_repo(py_wasm, rules_venv_py_wasm_cpython_3_14_trampoline = "my_cpython_wasi")

or, for a checkout on disk, --override_repository=rules_venv++py_wasm+rules_venv_py_wasm_cpython_3_14_trampoline=<directory>. The repositories are rules_venv_py_wasm_cpython_<X_Y>_<variant> (the build tree: libpython3.X.a, pyconfig.h, Modules/**/*.a; one per variant of the version, the flag choosing among them), ..._cpython_<X_Y>_<variant>_stdlib (lib/python3.X/**/*.py), rules_venv_py_wasm_wasi_sdk_<release>_<host> and rules_venv_py_wasm_wizer_<host>; a replacement provides the same targets as the BUILD files in extensions.bzl.

py_wasm_module

load("@rules_venv//python/wasm:defs.bzl", "py_wasm_module")

py_wasm_module(name, deps, entry, exports, initial_memory, preinitialize, python_version,
               stack_size, strip)

Build a self-contained WebAssembly module embedding CPython and Python sources.

The output, <name>.wasm, imports nothing and exports memory, allocate and one function per entry of exports; the module documentation of defs.bzl gives the calling convention. Each export calls the function of the same name in the entry module with the call's input as bytes and returns what it returns: bytes, or (bytes, code) to set the return code. An exception becomes return code 2 with the traceback in the output.

The module holds the sources of deps as a venv would import them, the standard library as bytecode, and, by default, a snapshot of the interpreter taken after the entry module was imported, so that a call does not pay for start-up. The CPython is the one of python_version, which also selects the rules_python toolchain the module is built with. See the module documentation of defs.bzl and py_wasm_toolchain.

py_wasm_toolchain

load("@rules_venv//python/wasm:defs.bzl", "py_wasm_toolchain")

py_wasm_toolchain(name, clang, compiler_files, cpython_libs, linkopts, pyconfig, python_version,
                  stdlib, sysroot, wizer)

Declare what py_wasm_module builds with: a C compiler for wasm32-wasi, a CPython built for it, and optionally Wizer.

rules_venv registers toolchains of this kind for Python 3.13 and 3.14 on Linux, macOS and Windows hosts from archives it fetches (see extensions.bzl); a module that wants a compiler or a CPython of its own declares one and registers it with register_toolchains or --extra_toolchains.

A toolchain is for one Python version: the headers that compile the module's host code and the interpreter that produces its bytecode are the rules_python toolchain's, so the two must be the same X.Y. Registering a toolchain with rules_python's is_python_X.Y as a target_setting, as below, makes it eligible only then, and a module's python_version selects it.

Requirements: clang must be the clang of a wasi-sdk (this rule fails on any other driver), of the release that built cpython_libs, so that their wasi-libc match; cpython_libs holds libpython3.X.a and the static libraries of the modules compiled into it; pyconfig is that build's pyconfig.h, which stands in for the host one of the rules_python toolchain's headers; linkopts names what that build links against beyond libc, by default what CPython's own wasm32-wasi configuration uses.

load("@rules_venv//python/wasm:defs.bzl", "py_wasm_toolchain")

py_wasm_toolchain(
    name = "py_wasm_toolchain",
    clang = "@my_wasi_sdk//:bin/clang",
    compiler_files = "@my_wasi_sdk//:all_files",
    cpython_libs = "@my_cpython_wasi//:libs",
    pyconfig = "@my_cpython_wasi//:pyconfig.h",
    python_version = "3.14",
    stdlib = "@my_cpython_wasi_stdlib//:stdlib",
    wizer = "@my_wizer//:wizer",
)

toolchain(
    name = "toolchain",
    exec_compatible_with = ["@platforms//os:linux", "@platforms//cpu:x86_64"],
    target_settings = ["@rules_python//python/config_settings:is_python_3.14"],
    toolchain = ":py_wasm_toolchain",
    toolchain_type = "@rules_venv//python/wasm:toolchain_type",
)
